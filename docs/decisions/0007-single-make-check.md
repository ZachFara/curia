# 0007. One `make check` for the hook and CI

Status: accepted (Phase 1 setup)

## Context

When the pre-commit hook and CI run different commands, they drift: something passes locally and fails in CI, or CI quietly checks less. The owner requires one check command wired into both.

## Decision

- `make check` is the only gate. In order: install pinned tools, gofumpt (fail on diff), golangci-lint, complexity limits, package boundaries, the suppression ban, `go vet`, staticcheck, `deadcode -test`, the layout check, `go test -race ./...`. Each step prints a `==>` heading.
- The lefthook `pre-commit` hook runs exactly `make check`.
- CI (`.github/workflows/ci.yml`, GitHub Actions, `ubuntu-latest`) checks out, sets up Go from `go.mod` (its `toolchain` line), restores the `.bin/` cache, installs tmux with apt so the real-tmux test runs, and then runs exactly `make check` as its only check.
- The CI job and its status check are both named `check`. Branch protection on `main` requires that name, so it must not be renamed.
- Tool versions come from the Makefile in both places (decision 0002).

## Consequences

- Changing what is checked means editing the Makefile only; hook and CI follow automatically.
- `go test -race` needs cgo on Linux; `ubuntu-latest` ships gcc. The race detector is a test-time tool and does not conflict with the pure-Go rule for the binary (decision 0001).
- There is deliberately no `go mod tidy` check (decision 0009).

Amended 2026-11-19 (owner, ticket D-3, answer "D", then D-11): the pre-commit hook no longer runs `make check`. Today it runs `make check-fast`: the static gates (`check-static`) and `go build ./...`, no tests and no machine-wide test lock. This replaced two earlier forms, both recorded here: the original "hook runs exactly `make check`", and D-3's first version of `check-fast`, which also ran `go test -race` (latency tests skipped) of the packages the staged files touch. Why: every commit in every worktree ran the whole gate (about 12 minutes) behind one lock, so eight agents waited about 90 minutes while CI ran the same suite again; and the touched-packages tests still took about 7 minutes for `cmd/curia` alone under load, so D-11 (answer "A") dropped tests from the hook. `make test-staged` runs the touched packages' tests by hand. CI is the full gate: it runs every test and is required on `main` and on every `plan-*` branch (GitHub ruleset "plan branches: CI must pass"; `main`'s branch protection, which also requires the branch to be up to date, D-4). `make check` is unchanged and remains the command for the full gate by hand. The "hook and CI run the same command" rule above no longer holds; decision 0005's line on the hook is amended the same way.

Amended 2026-11-19 (owner, ticket D-3 answer "D", and D-1): CI runs the same gate as parallel jobs, each a Makefile target that `make check` also runs (`check-static`, `test-unit` split into `cmd/curia` and every other package computed with `go list`, `test-latency` alone on its own runner), plus a final job named `check` that needs all of them and fails unless every one succeeded. The required status `check` is that aggregate job. `make check` is unchanged and still the full gate by hand.

2026-11-20 (owner, D-15, answer "C"; revised 2026-11-20): a CI latency gate blocks only if an automatic rerun also fails, and the rerun runs on a FRESH runner. The first design (`scripts/ci-retry-once.sh`, the same command twice inside one job) was removed: on PR #193's own run a slow runner made both attempts fail within 13 minutes ("the machine is too slow for this gate"), and a retry on the same machine cannot help. Now `.github/workflows/ci-rerun.yml` (trigger `workflow_run` of `ci`, `completed`; permissions `actions: write` only; no checkout, no third-party action) runs `gh run rerun --failed` once when the run failed on attempt 1 and every failed job other than `check` is a `latency` shard; on attempt 2 it does nothing, so a second failure blocks, and any failed unit or static job means no rerun. It writes the rerun (or why not) to its own job summary, and a rerun `latency` job prints a `::warning::` that it is an automatic rerun, so flakes are counted. Limits: a `workflow_run` workflow runs from the default branch's copy, so this takes effect only once it is on `main` (before that a failed latency shard blocks, as before #193, and a manual rerun is the remedy); a manual rerun is attempt 2 or later and is not rerun again. Second owner decision, same day ("too slow = could not measure"): a gate whose reference workload is over the 2x allowance ("reference p95 ... over the 2x allowance: the machine is too slow for this gate") is no longer a failure of the code but "could not measure" (`internal/latency`: `Outcome` Pass, Fail, CouldNotMeasure; a real failure anywhere wins; the 2x allowance, thresholds, batches and the pass/fail rule on an acceptable machine are unchanged). The verdict then ends with the line `LATENCY-COULD-NOT-MEASURE`. CI treats that job like a failure on attempt 1 (rerun once on a fresh runner); on attempt 2, a real failure blocks, and "could not measure" again also leaves the job failed (nothing unmeasured merges as a pass) with an `::error::` and job summary saying it was never measured and needs a manual rerun, not a code fix. By hand, `make test-latency` reports it as such and exits non-zero. Local `make test-latency` stays a single run.

2026-11-19: CI shards the `cmd/curia` unit tests (4 shards by test name) and the latency step (3 shards by package, each still `-p 1`), computed by `scripts/shard.sh`; `make check-shards` (in `check-gates` and CI `static`) fails unless the shards partition the set. `make check` still runs everything unsharded.

2026-11-20 (owner decision, faster CI, Ruling 191): a run took about 7.5 minutes, set by its slowest job; the goal is about 4 with no gate, threshold, test, batch count, spacing or race flag changed. (1) Latency shards go from 3 to 6 and are assigned by gate (`package test` lines, heaviest first onto the lightest shard, by the rough seconds per pass in `scripts/latency-weights.txt`; count balance left one shard at 7m56 against 3 to 4 min for the others; a gate without a weight counts as 15 s and `make check-shards` warns; one gate, `TestStopLatencyWithMessages` in `internal/hook`, takes about 65 s of the ~300 s of a pass and so sets the floor), not by package: only three packages hold gates, so per-package sharding could not use more than three runners. (2) `internal/store` runs alone as job `unit-store`; `unit-rest` is every other package but `cmd/curia` (`scripts/shard.sh list rest`); `make check-shards` fails unless `cmd/curia`, `STORE_PKG` and `unit-rest` are exactly `go list ./...`. (3) `unit-cmd` goes from 4 shards to 6. The counts are `LATENCY_SHARDS` and `CMD_SHARDS` in the Makefile only; the `plan` job publishes the matrices from `make shard-matrices`. (4) Docs-only changes skip the test jobs (unit and latency); `static` always runs. The first job `plan` decides `docs_only` on pull requests from `git diff --name-only --no-renames <base sha> HEAD` (`scripts/ci-docs-only.sh`); a push, or a diff that cannot be computed, is not docs-only. Docs-only means every changed file is `**/*.md`, `docs/**` or `LICENSE`, and none is under `.github/` or `scripts/`, in any `testdata/` directory, or a file a `go:embed` pattern selects (`internal/install/skill/SKILL.md`, `internal/store/migrations/`); an empty list or any doubt runs everything. No workflow-level `paths` filter is used, since it would leave the required `check` pending. `check` accepts the four test jobs as skipped only when `docs_only` is true (and then still needs `plan` and `static` to succeed and nothing else skipped); otherwise it requires every job to succeed as before.
