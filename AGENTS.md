# AGENTS.md

Read this first. It is the working agreement for every human and agent in this repository. CLAUDE.md points here.

## What Curia is

`curia` is one Go binary that turns tmux into a control plane for parallel coding agents. Claude Code hooks call `curia hook <Event>`; the hook parses the payload, applies a pure state machine and upserts one row per session in a local SQLite store (WAL mode). Every view reads that store: `curia status` (status-bar badge), window markers, `curia next` (jump to the session that needs you), `curia ls`, and the `curia ui` popup / `curia sidebar`. Nothing scrapes panes. tmux is driven through a small `tmux.Client` interface so logic is testable without tmux.

Plan 5 gives Curia real numbers and its outside connections (spec F13 and F15 to F17); it is the last plan of V1. `curia ingest` reads one JSON document per turn (the contract is `docs/ingest-schema.json`) from cost-lens, and writes each session's cost and prompt-cache state plus account usage samples; it never fails its caller and nothing automatic depends on its numbers, since any local process may call it. `curia statusline`, registered by `curia install` only when the owner has no `statusLine` of their own (`--no-statusline` opts out), feeds the same path from Claude Code's status-line JSON and prints one line. From the samples the badge warns when the limit will land before the reset, and `curia usage` and the dashboard show who burns it; Curia then suggests pausing the lowest-priority running task (`P` then `y`, never automatic) and `curia spawn` defaults a new agent to the cheaper model under a warning (`--model` always wins). The cache values Plan 2's queue order waited for become real: a cache column on the dashboard and a stakes line in the phone push. `curia export obsidian` and the sweep after `curia decide` write decision notes into an existing vault folder (all ticket text inside code fences, never overwriting a note without Curia's marker); `curia export commons <id>` prints an Agent Commons entry and sends nothing; `curia task import --linear` runs one read-only query against the configured Linear URL with the key from `CURIA_LINEAR_API_KEY`; Codex sessions are tracked through `curia hook <Event> --agent codex`, spawned and resumed through `curia launch`, and never typed into. No MCP tool is added (still six). Curia computes no cost: there is one price table, in cost-lens.

Plan 4 closes the loop from a running agent to merged work and lets the owner leave the desk (spec F10 to F12). Reviews: the agent calls `complete_task`, the sixth MCP tool, which only says "this task is ready for review" and opens a row in the new `reviews` table (it runs no git and changes no stored task status); `curia review` (user-only, refused inside an agent session) shows its summary, diff, tests, decisions and unconfirmed assumptions, and `a` approves by running git itself (by default `git merge --no-ff --no-edit` of the task branch into the base branch in the owner's checkout, or `--pr`: push and `gh pr create`), `c` sends a change request to the agent as a Plan 3 message, `x` drops the task. An approval is bound to the commit that was shown (Ruling 125): the view passes the head it displayed, and the flag form `curia review <id> --approve` needs `--head <full commit id>` (Ruling 126). A task's `review` and `done` statuses are derived from its newest review and never stored on `tasks`. Pushes: a new blocking ticket or review is a row in the `pushes` outbox, sent over plain `net/http` to ntfy (opt-in: nothing is sent or opened without `[ntfy] url` and a device) by whichever Curia process that flushes is alive (each agent's `curia mcp`, or `curia serve`; a push queued when the last of them exits waits for the next one to start); quiet hours hold pushes back; the access token comes only from `CURIA_NTFY_TOKEN`. `curia serve` is an optional, owner-started endpoint that listens on `127.0.0.1:8787` unless an address is set explicitly (then loopback or a Tailscale address only, Ruling 127), with one route that answers a blocking ticket from a phone button through `deliver.Answer`, using a one-time token bound to one ticket (stored only as its SHA-256; Ruling 129 states what it rests on). `curia restore` reads the store after a reboot or tmux crash, shows its plan, and on confirmation opens one tmux window per lost session and runs `claude --resume` in it (Ruling 124: sessions that are not ended or ended with reason `other`; Ruling 130: not those whose pane was closed while tmux kept running, unless `--include-closed`). Every place that matches a session to a pane id also matches its tmux server (Ruling 133). The MCP server exposes six tools, none of which can decide, send, spawn, pause, approve or merge.

Plan 3 adds work for the agents and a way to talk down to them. Tasks are rows in a local `tasks` table (`curia task`, a Backlog.md import) whose stored status is only what the user sets (backlog, ready, dropped); running and needs_decision are derived from the sessions linked to the task by `CURIA_TASK_ID`, and the board (`t` in the dashboard) shows them. `curia spawn <id>` runs git and tmux itself (a worktree under `.curia-worktrees/`, a window, an optional `.curia/setup.sh`) and starts the agent through a hidden `curia launch`, which reads the brief from the store and `execve`s `claude`, so no task text passes through tmux's command parser; `curia pause`, `resume` and `clean` are user-only. Messages (`curia say`, `curia send`) are rows in a `messages` table delivered by the same three claims as decision answers (typed into an idle pane, handed over by the Stop hook, or fetched with the fifth MCP tool, `check_messages`); `curia say` routes an unaddressed message with one bounded `claude -p` call, or turns it into a standing rule (a decided `decisions` row with no options) or a task. The MCP server exposes five tools, none of which can decide, send, spawn or pause. Agent Teams are read from Claude Code's team config when a view or `curia mcp` refreshes and shown as one unit; only a team's lead may raise a ticket.

Plan 3's user guard (`userOnly`, `cmd/curia/decisions.go`) decides who is the user: `say`, `decide`, `decisions edit`, `install`, `uninstall`, `messages cancel`, `routing reset`, `setup approve`, `pause`, `resume`, `clean` and the task-writing commands run only for a person at a terminal, and `curia send` labels a message "from the user" only then. It stops mistakes and naive misuse; it is not a security boundary (see "The user guard" below and ADR 0021).

Plan 2 adds decisions. `curia mcp` is a stdio MCP server, one process per Claude Code session, whose four tools let an agent search precedent and raise, check or withdraw a decision ticket in the store's `decisions` table; no MCP tool can answer one. `curia decide` (a popup, or flags for scripts) is the only place an answer is written, and it refuses to run inside an agent session; `curia decisions` (`ls`, `edit`) lists and curates tickets and is user-only too. The status badge reads `D<n> Q<n> W<n> R<n>` (open blocking tickets, answers a live session has not yet received, waiting sessions, reviews). An answer is delivered at most once, by one of three paths, each a claim in one write transaction: `curia decide` typing it into the agent's idle pane, `curia hook Stop` blocking the stop with the answer as its reason, or the agent's own `check_decision` (which also returns an answer already delivered).

## Setup, build, test, lint

Go 1.26 is required (`go.mod` pins `toolchain go1.26.11`). On the dev Mac it is a keg-only Homebrew formula and is **not on PATH by default**. Before running anything, in every shell:

```sh
export PATH=/opt/homebrew/opt/go@1.26/bin:$PATH
```

Never hardcode that path in the Makefile, hooks, scripts or CI; they call plain `go`.

Once per clone or worktree:

```sh
lefthook install      # installs the pre-commit and commit-msg hooks
```

Commands:

| Command | What it does |
| --- | --- |
| `make check` | The full gate, run by CI and by hand. Runs, in order: pinned tool install, gofumpt (fail on diff), golangci-lint, complexity limits, depguard boundaries, the suppression ban, `go vet`, staticcheck, `deadcode -test`, the layout check, the latency-name check, then `go test` in two phases (every test except the latency gates, packages in parallel; then the latency gates alone, `-p 1`, so they do not measure other packages' load; Ruling 134). All gates run under a lock shared by every worktree of the repository, so a check may wait for another worktree's. CI runs the same gate as parallel jobs (`make check-static`; `make test-unit` as `cmd/curia` and all other packages; `make test-latency`, with `cmd/curia` sharded by test name and the latency packages by package in CI only, `scripts/shard.sh`; `make check-shards` fails if a shard set is not a partition) and a final aggregate job `check`, the required status, that fails unless all of them succeeded; the pre-commit hook runs `make check-fast`. |
| `make check-fast` | The pre-commit hook. No lock. All static gates (including `deadcode`) and `go build ./...`. Static checks and build only, no tests: run `make test-staged` (the touched packages' tests, `scripts/staged-tests.sh`) or a narrow `go test -run` yourself; CI runs every test and is required to merge. Seconds. |
| `make fmt` | Rewrite Go files with gofumpt (convenience; the gate only checks). |
| `make build` | Build `./curia` (gitignored). |
| `go test -race ./internal/<pkg>/ -v` | Run one package's tests while iterating. |
| `make tools` | Install the pinned tool versions into `.bin/` (done automatically by `make check`). |

Rules for the toolchain:

- Never run `go mod tidy` during Plans 1 to 5. Every dependency is already in `go.mod` and `go.sum` (decision 0009) and Plans 2 to 5 add no module (decision 0011; Plan 3 parses Backlog.md by hand and runs the router as a subprocess; Plan 4 sends ntfy pushes and serves its endpoint with the standard library's `net/http`). No task edits `go.mod` or `go.sum`.
- No test-helper modules (testify, teatest and so on): tests use the standard library plus the package's own dependencies. Use real dependencies in temp dirs: SQLite files under `t.TempDir()`, a real tmux server on its own socket (`tmux -L <name>`) where tmux is installed.
- gosec is on (except G204): `filepath.Clean` paths before opening them, and write files with mode `0o600`.
- Worktrees live under `.worktrees/` (gitignored). Each one has its own `.bin/`, so its first `make check` builds the tools (about a minute). depguard matches files by absolute path and its `e2e` rule matches any path segment named `e2e`, so no directory on the path to a worktree may be named `e2e`; use the branch slug, e.g. `.worktrees/plan1-t2-store`.
- Lint limits (decision 0002): cyclomatic complexity at most 15, cognitive at most 20, nestif at most 4, functions at most 60 lines and 40 statements (tests exempt from length only). Exported names need doc comments (revive).

## Conventions

- **One file per command in `cmd/curia/`.** `main.go` holds only the package-level `rootCmd` and `main`. Every later command lives in its own file in `cmd/curia/` (for example `hook.go`, `ls.go`) and registers itself in that file's `init()` with `rootCmd.AddCommand(...)`, so parallel tasks never edit `main.go`. Tests for a command go in the matching `_test.go` file and drive it through `rootCmd.SetArgs` / `SetOut`.
- **Shared files belong to the orchestrator alone** (from the owner's PARALLEL EXECUTION rules): "Shared files belong to you alone: PROGRESS.md, AGENTS.md, docs/decisions/, go.mod, go.sum, cmd/curia/main.go, the Makefile and CI config. An implementer that thinks one of these needs a change says so in its report; you make the change on plan-1 between waves." Here "you" is the orchestrator. The same applies to `.golangci.yml`, `lefthook.yml` and `scripts/`, which are part of the check configuration.
- **`.scratch/` is the only place for throwaway work**: probe programs, experiments, notes, temporary scripts. It is gitignored and invisible to the layout check. Never put throwaway files in the tree. The orchestrator empties `.scratch/` at the end of every wave. Go code in `.scratch/` is not part of the module's `./...` (directories starting with `.` are skipped); to try something against this module's dependencies, copy `go.mod` and `go.sum` into a `.scratch/<name>/` directory and build there.
- **Commits**: conventional commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`, `build:`, `ci:`, `refactor:` ...), subject at most 72 characters; enforced by the commit-msg hook. Branches: `feat/`, `fix/`, `chore/`, `docs/`; Plan 1 task branches are `feat/plan1-tN-<slug>`. Plan 2 task branches are `feat/plan2-tN-<slug>`, in worktrees `.worktrees/plan2-tN-<slug>`. Plan 3 task branches are `feat/plan3-tN-<slug>`, in worktrees `.worktrees/plan3-tN-<slug>`. Plan 4 task branches are `feat/plan4-tN-<slug>`, in worktrees `.worktrees/plan4-tN-<slug>`. Plan 5 task branches are `feat/plan5-tN-<slug>`, in worktrees `.worktrees/plan5-tN-<slug>`.
- **Plan 5 task merges and starts.** A Plan 5 task merges into `plan-5` when its named tests and `make check` pass and CI is green, and it is one commit; the orchestrator starts a task the moment every task on its Needs line has merged.
- **PRs** use `.github/pull_request_template.md`: what changed, why, how it was tested.
- **No per-task review in Plan 4.** Reviews happen only at the final PR. A task merges when its named tests and `make check` pass and CI is green.
- **One commit per task, cheap checks first.** Before the single gated commit, run on your own packages only `gofumpt -l`, `.bin/golangci-lint run ./<pkg>/...`, `go vet` and the focused `go test -race` of the task's steps, and fix what they show. The pre-commit hook then runs `make check-fast` (D-3); CI runs the whole `make check`. A task is one commit unless the gate itself fails.
- **The gate lock is a fair queue.** Every worktree's `make check` waits its turn behind the shared lock: wait, never start a second run, and do not pipe `make check` output through `tail` (it hides the output until the run ends).
- **Gate economy** (a commit no longer waits for the lock: the hook runs `make check-fast`, D-3; only a hand-run `make check` queues). Do not use `make check` to find problems. Before the first commit run the cheap steps on your own packages: `make fmt`, `golangci-lint run ./<pkg>/...`, `go vet ./<pkg>/...`, `go test -race ./<pkg>/...`, and `bash scripts/check-layout.sh` for a records change. Run `make check` by hand only when you want the full gate before CI. Make one commit per task (a second only if CI or the hook finds something), commit in the foreground with a long timeout, and never start a second `make check` while one of yours waits. Merge `origin/plan-N` before the commit so the gate queues fairly (the lock is a FIFO queue, `scripts/with-test-lock.sh`).
- **No orphan waiters.** Never start a background loop that waits for "no `make check`, `git commit` or `gh pr checks` process anywhere" (`until ! pgrep -f …`): other agents always have one running and `pgrep -f` matches the loop's own command line, so it never ends (eleven were left running for 14 hours). Wait for your own commit in the foreground, or on its process id; wait for CI with `gh pr checks <n> --watch` in the foreground. Every wait has a deadline and watches only your own process id or PR. Before reporting, stop every background command you started.

## Things learned while building

- **Read-modify-write on a session goes through `store.UpdateSession`.** It loads the row, calls your function and upserts in one `BEGIN IMMEDIATE` transaction. Never pair `GetSession` with `UpsertSession` to change a row another process may be writing; `UpsertSession` is a blind overwrite. The function passed to `UpdateSession` must not call the store.
- **Timestamps in the store are fixed-width UTC text with 9 fractional digits.** Compare times as `time.Time` in Go; never write a timestamp with another layout.
- **An empty pane is stored as NULL.** `MarkSeen("")` and `EndOthersInPane("", ...)` change nothing, by design: a session started outside tmux is in no pane.
- **SQLite WAL on a fresh file:** several processes opening a new database at once get `SQLITE_BUSY` from the WAL switch without waiting for `busy_timeout`; `store.Open` handles it. Do not set `journal_mode` anywhere else.
- **tmux `display-message` expands both `#` formats and `%` strftime sequences.** `tmux.Client.DisplayMessage` escapes both; never call tmux with untrusted text any other way. With an unknown `-t` target, tmux can exit 0 with empty fields.
- **Tests that start a real tmux server use a per-run socket** (`curia-test-<pid>`), because several worktrees run `make check` at the same time.
- **Files the user owns may be symlinks into a dotfiles repo.** `internal/install` resolves symlinks before its atomic rename and never overwrites an existing backup.

- **tmux reads a command argument that is `;` or ends in `;` as a separator and runs the next argument as a tmux command; several arguments after the flags of `new-window` or `new-session` are executed directly, without a shell; `-e NAME=value` sets a variable for that pane only** (tmux 3.8, at the desk). Untrusted text is never an argument to tmux.
- **tmux 3.8 keeps `.` and `:` in a session name, which then cannot be targeted;** Curia builds session names from `[A-Za-z0-9_-]` and targets them as `=<name>:`.
- **`git worktree remove` refuses a worktree with modified or untracked files, and silently deletes one that holds only ignored files; `git branch -d` refuses a branch a worktree has checked out** (git 2.56.0, at the desk).
- **`git rev-parse --path-format=absolute --show-toplevel --absolute-git-dir --git-common-dir` gives the worktree, its git dir and the main repository's git dir in one process.**
- **A session's `repo` is the main repository; its `worktree` column holds the linked worktree** (decision 0020). A session's task comes from `CURIA_TASK_ID`.
- **The team columns of `sessions` are written only by `store.SetTeams`;** `upsert` leaves them out on purpose.
- **A standing rule is a decided `decisions` row with no options;** nothing else marks it (decision 0018).
- **Claude Code 2.1.323's `--help`** lists `-w/--worktree [name]`, `--tmux` (requires `--worktree`), `--session-id`, `--safe-mode`, `--no-session-persistence`, `--tools`, `--json-schema` and `-r/--resume`, and does not list `--teammate-mode`.
- **SQLite 3.51.0 (the system `sqlite3`) runs the `0004_tasks.sql` DDL** as one multi-statement script in one transaction, and `decisions_fts` passes `integrity-check` afterwards.
- **`git merge` runs the repository's commit-msg hook on the merge commit; a failed hook leaves `MERGE_HEAD` behind, which `git merge --abort` clears** (git 2.56.0, at the desk).
- **`git merge` with an unrelated local change in the checkout succeeds and keeps the change, and refuses when the change overlaps** (git 2.56.0, at the desk).
- **`git diff --stat <base>...<branch>` and `git push <remote> <branch>:<branch>` work from the main checkout without the worktree;** `git symbolic-ref --short -q HEAD` exits 1 on a detached head, and `git push --set-upstream <remote> <b>:<b>` works against a bare repository (git 2.56.0, at the desk).
- **tmux 3.8's `#{socket_path}` names the server** (an absolute path under `/private/tmp/tmux-<uid>/`). Plan 4 records it in `sessions.tmux_socket` on a session's first event only; an empty value means unknown.
- **A derived `review` or `done` comes from the task's newest review and is never stored on the task** (decision 0023). `tasks.status` keeps its Plan 3 `CHECK`.
- **The action token of a push is stored only as its SHA-256** (decision 0024); the clear token exists only in the outgoing request and is never logged.
- **SQLite 3.51.0 runs the `0005_reviews.sql` DDL** (applied after Plan 3's 0004) as one script in one transaction; `'R-' || (SELECT COALESCE(MAX(n), 0) + 1 FROM reviews)` with `RETURNING id` yields `R-1`, a second pending review of one task fails on `reviews_one_pending`, and `decisions_fts` passes `integrity-check` afterwards.
- **The marker option's new value draws a blue dot, a red dot or nothing** when appended through `#{E:@curia_marker_format}` (tmux 3.8, at the desk); Plan 4 changes only the value of `@curia_marker_format`.
- **The ntfy URL comes only from the config file, never from a flag or an argument.** With the pinned golangci-lint and this `.golangci.yml`, an `http.NewRequestWithContext` on a URL read from the config file, its `client.Do` and a `net.Listen` on a config address pass; the same request with a URL derived from a command-line argument is reported as `G704: SSRF via taint analysis`. No suppression is needed or allowed.
- **Claude Code 2.1.325's `--help`** lists `-r/--resume [value]` and `--fork-session` ("create a new session ID instead of reusing the original"), which implies a resume keeps its id (probe R1 confirms).
- **Command wiring lives in `cmd/curia/common.go`** (load config, open the store, open the log file) and git plumbing in `cmd/curia/git.go`. Reuse them; do not write a second copy in a new command.
- **Any test or code that runs `git` must drop git's repository-local `GIT_*` variables** (`gitEnv` in `cmd/curia/git.go`). lefthook's pre-commit exports `GIT_DIR`, so an unguarded `git init` in a test acts on the real repository.

The sequence Curia follows around an approval's merge (`reviewApprove`, `reviewApproveReady`, `reviewMergeReady`, `reviewMerge`, `reviewMergeDone` and `reviewMergeFailed`, `cmd/curia/review.go` and `review_git.go`; every git call is an argument vector with validated names; the ones that change something run in their own process group, output in unlinked temp files):

1. The user-only guard; the review is pending and its task not dropped; the method is merge or pr; `seen` is a full commit id (the view's shown head, or the flag form's `--head`).
2. Found-done check: if the review holds an intent to merge whose head is `seen`, the branch is still at it and `rev-list --count refs/heads/<base>..<head>` is 0, the review is recorded merged (for a pull-request approval too) and no git that writes runs.
3. `reviewCheck`: branch, `refs/heads/<base>`, agents idle, worktree clean, commits beyond the base, diff stat; `seen` must equal the branch head.
4. Before claiming, every action (`reviewEarlierMerge`, Ruling 137): an intent to merge younger than the 10-minute hold is refused as busy; an older one, with `MERGE_HEAD` or staged changes in the checkout, is refused as "may still be running git there". Then, for a merge (`reviewMergeReady`): the base is checked out (`symbolic-ref -q HEAD` is `refs/heads/<base>`), no merge, rebase, cherry-pick, revert or bisect is under way, and `diff-index --cached --quiet HEAD --` is clean. A refusal here touches no intent. Drop and request changes run `reviewEarlierMerge` before `CloseReview`.
5. Claim: `ClaimReviewIntent`, one conditional UPDATE that writes the intent (approved_how, head, diff_stat, time); refused while another intent younger than the hold stands.
6. `reviewMerge`: names and checkout checked again; the state before is read (HEAD, `status --porcelain --untracked-files=all`, the index against HEAD, and every path `git diff --raw` lists, by kind; more than 500 are not recorded and the merge still runs); staged changes refuse; the branch must still be at the head; `git merge-tree --write-tree --name-only --no-messages HEAD <head>` gives the expected tree T, a conflict is refused here (nothing changed), and on a git older than 2.38 T is unknown; `reviewCheckOnDisk` refuses a path the merge adds that exists on disk (Ruling 138); then `git merge --no-ff --commit --no-edit --no-autostash -m ... <head>` with `branch.<base>.mergeOptions` emptied and, when T is known, `pull.twohead=ort` through `GIT_CONFIG_COUNT` (`reviewMergeEnv`), under a 2-minute limit, stopped with SIGTERM and killed after 5 s.
7. Exit 0: `reviewMergeDone` records the review merged only when `refs/heads/<base>` contains the head (Ruling 136); otherwise nothing is recorded, the intent stays and the state and commands are printed.
8. Failure: `reviewMergeFailed` runs on a context detached from the caller's: it reads `MERGE_HEAD`, unmerged entries, HEAD and `index.lock`, then runs exactly one of: `git merge --abort` after a conflict (unmerged entries); `git merge --abort` after a refusing hook or a git stopped after the merge commit, and `git reset --merge` after a merge cut short before `MERGE_HEAD`, each only when the proof of Ruling 128 holds (T known, no `index.lock`, the index equals T, or the merge commit's tree when HEAD moved, and every differing working-tree file differed before with the same content); or nothing, printing the state and the commands. A reset also needs HEAD unmoved, the index clean before, and git stopped by Curia or by a signal. "As it was" is said only after re-reading HEAD, the index, the status and the modified files' content. Afterwards a head found in the base is recorded merged at once; otherwise the intent is kept when the checkout was left as found, else the earlier intent is put back or the claim cleared.
9. The pull-request path is the same up to step 5, then pushes `<commit>:refs/heads/<branch>` and runs `gh pr create` (an existing pull request is adopted only under Ruling 131).
10. `curia review` and `curia ui` hold SIGHUP and SIGTERM (the flag form SIGINT too) while a review action runs and wait for it (at most 7 minutes) before exiting, so a closed popup does not cut an approval short; a SIGKILL of Curia leaves git running to its end and the intent records what was approved.
