## Plan 5 Rulings

Format: N. Ruling: what — why — cost if wrong. **Plan 5's rulings start at 162.** `main` holds Rulings up to 139; the spec-additions pull request #142 (not merged, under the owner's review) uses 140 to 161. Plan 5's working ledger called its first eight rulings P5-R1 to P5-R8; the later ones are dated entries and owner decisions (D-1, D-3, D-4, answered through Curia tickets). They are recorded here in the order they were made, each with its ledger name in parentheses. Rulings 169, 170, 174 (the CI split), 176, 177 and 179 describe pull requests that had not merged into `plan-5` when this was written (see "In progress on 2026-11-19" in the status); until each merges, the ruling states the decision, not the code.

162. Ruling (P5-R1, probe S1, 2026-11-15; amends the spec's F15, which says the status line has no cache field): the status-line payload carries the session's prompt-cache state (`prompt_cache.expires_at` in Unix seconds, `warm`, `ttl`, `recache_tokens_if_cold`), and ingest takes the session's cache expiry from it (`expires_at` accepted from 7 days back to 2 hours ahead, or RFC 3339) — the plan's section 4.3 said there is no cache field and cache state would stay blank without cost-lens's push; the probe showed the fields in every payload from the first full response on, so F17's cache values are real in daily use — if wrong (Claude Code drops or renames the fields), the cache column and the stakes line go blank again, which is the pre-probe behaviour and breaks nothing; cache TTL on the probed account was 1 hour, not 5 minutes, so the "keep warm" windows are longer than the spec's examples.
163. Ruling (P5-R2, probe S1): a rebuild cost in dollars is unknown from the status line, which gives only tokens, and Curia keeps no price table, so the session stores `recache_tokens` (migration `0006_cost.sql`) and every place that would show dollars shows tokens when the dollar figure is unknown (`cold 85k tok`; the stakes line after PR #140) — an invented dollar figure would be wrong on every plan and model, and the spec's "one price table, in cost-lens" is kept — cost if wrong: the owner reads tokens where the spec shows dollars; a push from cost-lens (Open Question 8) restores dollars.
164. Ruling (P5-R3, probe S1): `curia statusline` always exits 0 and prints its line, targets well under 300 ms, does no network and starts no process, and is NOT user-only (classified with a reason in `TestEveryCommandIsClassified`, like `ingest`) — Claude Code kills a status-line run when a newer one starts (every 0.3 to 0.5 s in a busy turn), blanks the line on a non-zero exit, and runs the command inside the agent's environment (`CLAUDECODE=1`, `TMUX_PANE`, `CURIA_TASK_ID`), where the user guard would refuse it — cost if wrong: a slow run is killed before it prints, again and again; a user-only guard would blank the line in every session.
165. Ruling (P5-R4, probe C2): the cost-lens analyzer counts a worktree's sessions only under the worktree's own path (`--project <worktree>`, by the worktree's branch name; `--project <main repository>` returns no branches for them), so branch cost in a review is always asked with the task's worktree path, also after the worktree is removed (the analyzer still answers); Curia reads only `currentProject` from the output and never stores or logs the rest (which names the developer's other projects and recent session titles), and runs the analyzer in the background with a deadline, never on a render or hook path (8 to 15 s a run) — cost if wrong: a task whose `worktree` column was cleared (`curia clean`) shows no branch cost; a run that reads more than `currentProject` would keep other projects' names.
166. Ruling (P5-R5, probe X2): Curia never rewrites Codex's configuration: it never calls `codex mcp add` when any `curia` table exists in the Codex config (`codex mcp add` silently overwrites a same-name entry and rewrites the user's inline tables as sub-tables, and even `codex --help` writes into `CODEX_HOME`), prefers a minimal append of its own table over invoking `codex`, and never touches another table — cost if wrong: a user's Codex servers could be rewritten; the price is that Task 10 (held for probe X1) is a hand-written TOML edit with its own tests.
167. Ruling (Task 9 and the dispatch, 2026-11-15): `curia install` adds the status line only when the owner has no `statusLine` key, never replaces a foreign one (it prints a chaining hint instead; `--no-statusline` skips it and prints the hint too), recognizes its own entry by the hooks' narrow rule and repairs a stale one for another binary path on re-install (a fourth state, `StatusLineUpdated`), and every command Curia hands the user is plain POSIX `sh` (`… | <bin> ingest --statusline; …`), because macOS `/bin/sh` (bash 3.2 in POSIX mode) and dash reject `>(…)` — which shell Claude Code uses for `statusLine` is unverified — cost if wrong: a foreign status line is never overwritten, so the worst case is no Curia line; a hint using `>(…)` would break the user's own status line.
168. Ruling (P5-R6, Task 16): a failed Linear page imports nothing (all or nothing; a retry imports everything), accepted — a partial import after a failed page would leave the developer unsure which issues arrived, and a re-import updates only title, body and tags, so a retry is safe — cost if wrong: one bad page of four blocks the whole import until it passes; the 200-issue cap (4 pages of 50) is inferred from the count, and a `started` issue is skipped.
169. Ruling (P5-R7, Task 17 and the spawn fix, PR #140 in progress): the cheaper model chosen under a limit warning applies to that one spawn only and is not stored as the task's `agent_model`, and a stored model is used only with the agent it was stored for (never `--model sonnet` to Codex; changing a task's agent clears its model) — a stored cheap model would silently follow the task after the limit reset, and a Claude model name given to Codex fails at start-up; Task 17 also found that an option-like `--model` value went straight into the window command (now refused) — cost if wrong: after a warning a task whose model is not stored needs `--model` again on its next spawn; no migration is needed.
170. Ruling (P5-R8, Task 17 and the spawn fix, PR #140 in progress): `curia restore` resumes each session with ITS agent (`sessions.agent`, Task 8) and never plain `claude --resume` for a Codex session; until a Codex resume path is built, it skips a non-Claude session with a line giving the command to run by hand, and also skips a Claude session whose task now runs another agent (amends decision 0031's "an unlinked Codex session is not restored") — resuming a Codex session with Claude's command opens the wrong program on a session id it does not know — cost if wrong: a Codex session lost to a reboot is brought back by hand.
171. Ruling (owner's report, fix wave, 2026-11-19; PR #141, merged): `curia uninstall` also undoes, in each reachable running tmux server, only what Curia's snippet set (its pane-focus-in hook entries, its own key bindings, its status-right segment), one line per action or item left, and prints the commands to run by hand when no server is reachable; `curia install` replaces entries that name an old binary path — the owner saw `curia seen %N returned 127` on every pane switch once the binary was gone, because the old uninstall only removed the files and left the running server loaded — cost if wrong: a value the owner set to the same text as Curia's would be unset (checked by value, so only Curia's own); a key binding the owner bound by hand stays: a key is unbound only when its binding runs Curia's own command (checked in `internal/install/tmuxserver.go`, including the by-hand commands, which `grep` for Curia's command before they unbind), and one the owner's `~/.tmux.conf` binds outside the curia block is left out.
172. Ruling (owner decision D-1, 2026-11-19, via a Curia ticket; overrides the orchestrator's assumption, nothing had been built on it): a latency gate passes on the MEDIAN of three batches, not on any one, with the same thresholds, sample counts and `-race`; if still flaky, the gate becomes the ratio to a reference workload measured in the same job — latency gates failed on shared runners and under local load on code that had not changed for the worse, and one noisy batch decided the run (Task 14's gate failed at 22 to 23 ms against 20; PR #135 fixed that one at its cause, the median is for the rest) — cost if wrong: a real regression that shows in one batch of three passes; the helper is a change to the shared latency test helper (in progress, not merged).
173. Ruling (ledger 2026-11-19, PR #143): test code uses made-up process ids above any real pid (`fakePID` = 1<<30 + n) and a test asserts the fake process table has no cycle — `userShellTable()` mixed `os.Getppid()` with made-up pids 9001 and 9002; when the runner's real parent pid equalled one, the computed-key entry overwrote it, the table became a cycle and 199 tests in `cmd/curia` failed with "parent processes are more than 64 deep" in CI (diagnosis from the log and code; the rerun was green) — cost if wrong: a flaky pid collision returns on a machine whose pids reach 1<<30 (they do not on macOS or Linux defaults).
174. Ruling (owner decision D-3 = D, 2026-11-19; replaces decision 0007's "pre-commit and CI run exactly the same command"): the pre-commit hook runs `make check-fast` (every static gate, `go build ./...`, then `go test -race` without the latency tests of only the packages the staged files belong to, no lock; md-only commit about 12 s) and CI is the full gate, required on `main` and on every `plan-*` branch; CI is then split into parallel jobs (static, unit-rest, latency, unit-cmd) with an aggregate job still named `check` that passes only on four `success` results (PR #144, in progress: 8.1 minutes wall clock against about 10, because the critical path is `cmd/curia`'s tests alone, 8 minutes under `-race`) — an agent waited 10 to 12 minutes on every commit for a gate CI runs again; the mapping self-check is part of `make check` (PR #138) — cost if wrong: a defect that only a latency test or an untouched package's test shows reaches CI instead of the commit; the aggregate's failure path was not exercised on GitHub.
175. Ruling (fix wave: ledger items of Tasks 7 and 18; PR #139, merged): an export mark is guarded (`MarkExportedIf`: one transaction, so a rescope between the write and the mark leaves the decision due), a decision whose note name is taken by a foreign note is skipped and remembered in a `meta` row `export_skip:<id>` (no migration) so a sweep no longer re-runs the 500 lowest ids forever, `curia export obsidian --retry-skipped` tries them again, and answering in the dashboard's decide view starts a background sweep — without the guard a crash left a stale note marked exported, and with 500 or more foreign notes `--all` starved the rest — cost if wrong: a skipped decision stays out of the vault until `--retry-skipped`; the skip state is parsed with `substr` on a fixed 30-byte timestamp (deferred minors).
176. ## Plan 4 Rulings

Format: Ruling: what — why — cost if wrong. **Plan 4's rulings start at 124.** Rulings 97 to 123 were made during Plan 3's build and are recorded by Plan 3's records step, not here. Five rulings of Plan 4's working ledger were numbered 117, 118, 121 and 122 (in parallel with Plan 3's fix wave) and P4-R5 to P4-R10 (the owner questions of the final review, answered by default); they are recorded here, in order, as 124 to 135, and each entry names its ledger number. Where a later ruling amends an earlier one, both entries say so.

124. Ruling (probe R1, surprise 2; ledger 117): a session row records why it ended (`sessions.end_reason`, migration `0005_reviews.sql`; the hook stores the SessionEnd reason, a missing reason as `other`; the column is kept only while the row is ended), and `curia restore` offers the sessions that are not ended or that ended with reason `other` — `tmux kill-server`, a killed window and SIGTERM all make Claude Code exit cleanly and fire SessionEnd with reason `other`, so the plan's rule (every session that is not `ended`) found nothing to restore after a tmux crash; a deliberate `/exit` says `prompt_input_exit` and is not offered; only `kill -9` or a power cut leaves a row unended — `other` is also what a pane closed on purpose reports, so the rule offered those too (the final review's I5; **amended by Ruling 130**). A SessionEnd for an id with no row (a resume of an unknown id fires one) creates an ended row with reason `other`; restore's transcript check classes it "no transcript". An older binary's upsert leaves the column alone.
125. Ruling (Task 8's concern; ledger 118): an approval is bound to the commit that was shown: `Approve(ctx, id, head)` carries the branch head (a commit id) the review displayed, the command re-reads the branch head inside the approve step and refuses with "the branch changed since you looked; showing the new state" when it differs, then refreshes the view, and the merge (and, in pull-request mode, the push) uses the commit id itself, not the branch name — without it an agent that pushes a commit while the developer reads would have it merged unseen — one extra key press when an agent pushes during a review. The final review found the code stricter than the ruling: nothing can move between the check and the merge. **Extended by Ruling 126** to the non-interactive form.
126. Ruling (final review I1; ledger 121, amended): the non-interactive `curia review <id> --approve` requires `--head <commit id>` and the id must be the FULL id (40 hex digits, 64 for a SHA-256 repository, lower case); without it the command prints the branch head, its diff stat line and the exact command to run, and exits 1; with anything but the full id of the branch's current head it refuses and shows the full head; nothing is merged in either case — the flag form passed an empty head and merged whatever the branch was at when it ran, including a commit made after the developer last looked (probe `TestProbeFlagApproveMergesUnseenCommit`). The same ledger entry asked for a claim before the merge so two approvers cannot both act: it is the approval's recorded intent (approved_how, head and diff stat on the pending review, held 10 minutes; a second approver is refused while it stands). **Amended once:** the owner question of the final review (P4-R8, default yes) first allowed a prefix of at least 7 hex digits; an automated finding on the fix wave reversed it, and no prefix is accepted now. Cost: the developer copies a 40-character id (the refusal prints the whole command).
127. Ruling (final review I2; ledger 122 and P4-R9): `curia serve` listens on `127.0.0.1:8787` by default, with no automatic address detection of any kind; a non-loopback address is used only when set explicitly (`--listen` or `[serve] listen`), is still limited to the two Tailscale ranges, and prints one more start-up line; the documented setup is `tailscale serve` in front of the loopback address, with `[serve] public_url` set to the https URL it gives — the first build took the first interface address in 100.64.0.0/10, which is carrier-grade NAT space that ISPs and hotspots hand out, not only Tailscale, so strangers on such a network could reach the listener; the ledger's first form (detection only when the same interface also carries a Tailscale IPv6 address) was dropped as more than the setup needs (**supersedes the optional detection in ledger 122**) — the owner sets one address or runs `tailscale serve`; spec F11 and section 7 ("binds only to the Tailscale interface") no longer hold as written (amended there). Still open: plain `http` is allowed to any 100.64.0.0/10 literal for `ntfy.url` and `public_url` (Plan 4 deferred minors).
128. Ruling (final review C1, owner question 1; ledger P4-R5, tightened by P4-R10 and by the two re-reviews): a merge that would conflict is refused BEFORE it runs, from `git merge-tree --write-tree`; Curia undoes ONLY its own interrupted merge (`git merge --abort` or `git reset --merge`, nothing else), and only when the index equals the merge's expected tree, no `index.lock` is left, and every differing working-tree file differed before the merge with the same content; otherwise nothing runs, Curia prints the state and the commands (`git status`, `git merge --abort`, `git reset --merge`) and keeps the approval's intent; "as it was" or "nothing was merged" is said only after re-reading HEAD, the index, the status with untracked files and the content of every modified file and finding them equal to the state recorded before the merge; on a git older than 2.38 (no `merge-tree --write-tree`) the merge runs but is never undone; with more than 500 modified files the merge runs and only the undo is refused; accepted residual: a change staged in the tens of milliseconds between the last check and the undo is undone with the merge, and "as it was" is then not true of it — an approval's `git merge` that is cut short (popup closed, process killed, Curia's own 2-minute limit) left the merged files staged in the developer's checkout, and the plan's text was "never `git reset`"; the first form (P4-R5: only when the index was clean before the merge, compared with the recorded state) destroyed a change staged while a slow hook ran (C-A: git holds no `index.lock` during `pre-merge-commit`, so the check made before git started could not see what appeared later, and the comparison missed it too); the second re-review's fixes made the proof compare modified paths by kind (a deleted file, a symlink, a submodule's commit, a regular file's bytes) instead of running `git hash-object`, which exits 128 on the first three — if owner question 1 is answered no (Open Question 14), the undo is removed and Curia always prints the commands; if the proof is wrong, the developer's staged work is lost and Curia says the checkout is as it was; the undo is also refused, with the reason named, when a file could not be read, which can leave a developer with a checkout to clean by hand. Assumed unset: `submodule.recurse` (the undo would recurse into submodules).
129. Ruling (final review owner question 2; ledger P4-R6): a decision push's one-time token rests on the ntfy topic (in the action headers, so in ntfy's message cache and on the phone), and this is accepted on two written conditions: the topic is on a self-hosted server or is access-controlled (on ntfy.sh a topic name is the only secret, and whoever learns it reads every ticket and its token), and the endpoint is reachable only from the tailnet (`tailscale serve`, never Funnel or a public address, because the token is the only check); the README states both, and `curia serve` prints start-up lines that name them in the merged code (a loopback start says to put `tailscale serve` in front of it and never Funnel; a non-loopback one says to make sure the address is this machine's Tailscale address; and every start says the one-time token is the only check and to keep the topic private, self-hosted or access-controlled, and the endpoint on the tailnet) — probe N2 showed headers and body reach every subscriber unchanged, and the plan's design (a token per push, bound to its ticket and device, not to an option) needs them there — anyone who can read the topic can answer that one ticket once, within 24 hours, with any option the ticket offers (not only the three on buttons) while it is open and not irreversible; an agent on the same machine runs as the developer and can read the config and the topic, which is the accepted same-user limit. Irreversible tickets and reviews get no buttons.
130. Ruling (final review I5, owner question 3; ledger P4-R7): `curia restore` skips a session whose pane was closed while the tmux server kept running (the session started at or after the listed server's start and is not on another server), with the reason "its pane was closed while tmux kept running; reopen it with claude --resume <id> in <dir>", unless `--include-closed` — Ruling 124's rule also matched a window the developer closed, or killed with the dashboard's `x y`, and the confirmation is all or nothing, so after a real crash the developer could not take back the crashed sessions without the closed ones (**amends Ruling 124**) — a session whose pane died by itself on a server that kept running is skipped too and needs `--include-closed` or the printed command.
131. Ruling (final review I8, automated finding on the fix wave): an existing pull request is adopted as the approval's own only when it is open, from the task's branch into its base, not cross-repository, at the approved head exactly, with the title and body this approval would create (`task.PRTitle`, `task.PRBody`), and its URL is `https://<host>/<owner>/<repo>/pull/<n>` of the repository `git remote get-url <remote>` names; otherwise Curia records nothing and leaves the review pending (an error that names the pull request when head, base and branch match but title or body differ), and it never edits a pull request it did not create (no `gh pr edit`) — without any adoption, "approve again" could never succeed once the pull request existed (I8: a `gh pr create` that failed late, or a pull request opened by hand, left the review pending with `--drop` as the only exit); the first build already required an open pull request from the task's branch into its base, and an automated finding on the fix wave (valid) asked for the head, title and body as well, so that Curia never presents as its own a pull request it did not create — an SSH host alias (`git@github-work:o/r`) never matches github.com, so such a repository can never adopt its own pull request, and the body includes the tickets decided since the first attempt, so a ticket decided between two attempts makes Curia's own pull request look foreign (re-review M-8).
132. Ruling (live check defect 2): a confirmation key that arrives within 50 ms of another key is refused, and its wait restarts: the review view's approve and drop, and the decide view's irreversible confirmation (a `y` within 50 ms after another key is refused; a `y` that passes acts only when 50 ms go by with no other key, and a key within 50 ms after it refuses it) — an unbracketed paste of `y` plus a line break (`tmux paste-buffer` without `-p`) arrives as two key messages a millisecond apart and approved a real merge; a bracketed paste was already refused — a `y` followed 200 ms later by an unrelated key has already acted (asserted as intended), so the rule stops a paste, not a slow double-tap.
133. Ruling (final review I4; ledger "use the recorded session server"): pane ids are matched only together with their tmux server, everywhere: one rule, `fleet.OtherServer` (over listed panes, built on `fleet.OtherSocket`; the store's SQL repeats it as `sameServer`), used by the hook (`EndOthersInPane`), the dashboard and the board (jump and kill), `curia next`, `pause` and `clean`, `curia seen`, restore, delivery (`sharesPane`, `MarkSeen`, attention markers) and the user guard — Plan 4's tasks fixed reconcile, delivery, the guard and restore, and the final review reproduced six more places where a pane id alone could end the wrong session, switch to or kill another server's pane, or refuse typing because of a session elsewhere (pane ids repeat across servers: a fresh server numbers its first pane `%0`) — a session with no recorded server behaves as before until its next SessionStart; `reviewMarkers` and the settle path still apply markers with no known server (Plan 4 deferred minors). **Extends decision 0025.**
134. ## Plan 3 Rulings

Format: Ruling: what — why — cost if wrong. Rulings 94 to 96 were made 2026-11-13 after the owner's real tmux setup was damaged by `curia install`; they are implemented by the separate fix PR `fix/install-respects-tmux`, not by Plan 3's tasks. **Plan 3's probe rulings start at 97.** Rulings 97 to 103 came from the probes, 104 from the install fix, 105 to 109 and 111 from the build, 110 and 112 to 116 from the live checks and the final review, and 119, 120 and 123 from the fix wave's automated security findings. Where a later ruling amends an earlier one, both entries say so; where a ruling changed a plan decision, the entry names it.

94. Ruling: the tmux snippet never replaces `window-status-format`; it adds its marker to the format in effect — replacing the owner's format destroyed their window list — a window list that shows Curia's marker through the user's own format.
95. Ruling: Curia never rebinds a key the user has already bound; it binds only free keys or its own, reports the taken ones, and the keys are configurable — a binding that silently replaced the owner's own is damage `curia install` must not do — a user with every key taken gets no popup binding until they choose one. (Task 21's `prefix m` follows this: tmux binds `m` to mark-pane by default.)
96. Ruling: tmux options are changed only as far as needed — the snippet had set options the owner had already chosen — fewer settings from Curia, and a Curia feature that needs an option the user set differently reports it.
97. Ruling: a message's status is stored as `canceled` (US spelling; Go name `MsgCanceled`; the command `messages cancel` is unchanged), not the spec's `cancelled` — the misspell linter rejects "cancelled" and checks are never loosened — none beyond spelling. (Changes the spelling in spec F18's data line; every brief that said "cancelled", including migration 0004's CHECK constraint, was told.)
98. Ruling (probe P5): the Agent Teams config is `~/.claude/teams/session-<8 hex of the lead's session id>/config.json`, not named by the team name.
